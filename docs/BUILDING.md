# Building, testing and releasing Paperwing

## Repository layout

Paperwing is a fork of [BentoPDF](https://github.com/alam00000/bentopdf) that keeps BentoPDF's code
untouched and adds three layers on top:

| Path                     | What it is                                                                                                                                   |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `src/`, `public/`, …     | **BentoPDF** — the 100+ tool pages and all PDF processing (upstream code)                                                                    |
| `app.html`, `src/acro/`  | **Paperwing workspace** — tabs, Home, All tools, document view, shortcuts, preferences                                                       |
| `src/reskin/`, `reskin/` | **Integration layer** — Acrobat-style light/dark theme for every tool page, frame embedding, a Vite plugin that injects it all at build time |
| `desktop/`               | **Electron app** — window, `app://` protocol, file associations, native dialogs, packaging                                                   |

Paperwing modifies upstream code as little as possible: `vite.config.ts` (two lines registering
`reskin/vite-plugin-reskin.ts`) plus a few security fixes. Every change is listed in
[UPSTREAM-PATCHES.md](UPSTREAM-PATCHES.md); check it when merging a new BentoPDF release.

## Prerequisites

- Node.js **22** or newer and npm
- Windows 10/11 or macOS 12+ (Linux works for development; AppImage packaging is configured but untested)
- Google Chrome or Chromium for the end-to-end tests

```bash
npm ci                 # in the repository root (BentoPDF)
cd desktop && npm ci   # desktop shell
```

## Running

| Command (in `desktop/`) | What it does                                          |
| ----------------------- | ----------------------------------------------------- |
| `npm run dev`           | Build the web app into `../dist` and launch Paperwing |
| `npm start`             | Launch Paperwing using the existing `../dist` build   |
| `npm run build:web`     | Build only the web app (Vite, simple mode)            |

For fast UI work you can also run the Vite dev server from the repository root and open the
workspace in a browser:

```bash
SIMPLE_MODE=true npx vite          # then open http://localhost:5173/app.html
```

(On Windows `cmd`: `set SIMPLE_MODE=true && npx vite`.) In a browser, files open through the File
System Access API instead of native dialogs; everything else behaves the same.

## Testing

```bash
npx vitest run                         # unit tests (BentoPDF + src/tests/paperwing-shell.test.ts)
npx tsc --noEmit -p .                  # type check

# End-to-end UI tests (in desktop/), against a running dev server or preview:
PAPERWING_URL=http://localhost:5173 npm run test:e2e
```

The end-to-end suite (`desktop/tests/e2e.test.mjs`) drives the real interface in headless Chrome:
opening documents, Acrobat shortcuts, unsaved-change prompts, reopening closed tabs, running a tool on
the open document, theming of tool pages, and more. Set `CHROME_PATH` if Chrome isn't found.

## Screenshots

The README screenshots (`docs/screenshots/*.png`) are taken from the real interface, using the
sample documents in `docs/screenshots/samples/`. After a design change, rebuild and regenerate them:

```bash
cd desktop && npm run build:web
cd .. && npx vite preview --port 4173      # leave it running
cd desktop && PAPERWING_URL=http://localhost:4173 npm run docs:screenshots   # or only some: hero home
```

`social-preview.png`, the image GitHub shows when the repository is shared, isn't generated by the
script; it's uploaded in the repository settings.

## Packaging

| Command (in `desktop/`) | Output in `desktop/release/`                                           |
| ----------------------- | ---------------------------------------------------------------------- |
| `npm run dist:win`      | `Paperwing-Setup-<v>-x64.exe` and `Paperwing-Portable-<v>-win-x64.zip` |
| `npm run dist:mac`      | `Paperwing-<v>-mac-arm64.dmg` and `…-mac-x64.dmg` (must run on macOS)  |
| `npm run pack`          | Unpacked app folder only, for quick checks                             |

Packaging is configured in `desktop/electron-builder.yml`. The app icon is generated from
`desktop/build/icon.svg` (`icon.png`, 1024 px, is what electron-builder uses).

### Keeping the download small

- **LibreOffice is downloaded on demand.** `soffice.wasm.gz` and `soffice.data.gz` (~77 MB) are
  left out of the package. `npm run build:web` writes `desktop/engines.json` with their sizes,
  SHA-256 hashes and a release tag derived from their content (`engine-libreoffice-<hash>`). When a
  tool first asks for them, `main.cjs` downloads them from that release on GitHub, verifies the hash
  and caches them in the user data folder. The release workflow uploads them automatically.
  To test against a local copy, serve `public/libreoffice-wasm/` and start the app with
  `PAPERWING_ENGINE_BASE=http://localhost:<port>`.
- **Pre-compressed `.br`/`.gz` copies** that Vite emits for web servers are deleted after the build.
- **Chromium trimming:** English locales only (`electronLanguages`), maximum compression, and
  `scripts/after-pack.cjs` removes the DirectX shader compiler DLLs used only by WebGPU.

### Code signing (optional)

Builds are unsigned by default, which is why Windows SmartScreen and macOS Gatekeeper show a warning
on first launch (see [INSTALL.md](INSTALL.md)). To sign:

- **Windows:** set `CSC_LINK` (path/URL/base64 of a `.pfx`) and `CSC_KEY_PASSWORD`.
- **macOS:** set `CSC_LINK`/`CSC_KEY_PASSWORD` for a _Developer ID Application_ certificate, change
  `mac.identity` in `electron-builder.yml` from `'-'` to `null` (auto-discover) or your identity name,
  set `hardenedRuntime: true`, and add notarisation credentials (`APPLE_ID`,
  `APPLE_APP_SPECIFIC_PASSWORD`, `APPLE_TEAM_ID`) with `notarize: true`.

In GitHub Actions, add these as repository secrets and expose them as environment variables in
`.github/workflows/release.yml`, and remove `CSC_IDENTITY_AUTO_DISCOVERY: 'false'`.

## Releasing

1. Update `version` in `desktop/package.json` and add a section to `CHANGELOG.md`.
2. Update `docs/RELEASE_NOTES.md` (it becomes the GitHub release description).
3. Commit, then tag and push the branch and the tag (push only this one tag: GitHub doesn't start
   workflows when more than three tags are pushed at once):
   ```bash
   git tag v1.0.0
   git push origin main
   git push origin v1.0.0
   ```
4. The **Release desktop apps** workflow builds Windows and macOS on GitHub's runners (about
   15–25 minutes) and creates a **draft release** with all installers and a `SHA256SUMS.txt`.
   It also publishes the LibreOffice engine files to an `engine-libreoffice-<hash>` pre-release
   if that engine version hasn't been published yet. Leave that pre-release in place: installed
   apps download from it.
5. Open the draft on GitHub, check the notes and assets, and click **Publish release**.

The in-app update check compares against the latest _published_ release of the repository set in
`desktop/package.json` → `paperwing.repository`.

The Windows installer updates itself from the repository in `desktop/electron-builder.yml` →
`publish`, using the release's `latest.yml` and `.blockmap` assets, so keep those attached. Drafts
and pre-releases are invisible to it: installed copies start downloading only once a release is
published as the latest one. Don't replace an installer after publishing; `latest.yml` holds its
SHA-512, and a mismatch makes every update fail.

## Pulling in new BentoPDF versions

```bash
# upstream = https://github.com/alam00000/bentopdf (fetched without its tags, so BentoPDF's
# version tags never mix with Paperwing's)
git fetch upstream refs/tags/v2.9.0:refs/tags/upstream/v2.9.0
git merge upstream/v2.9.0            # the BentoPDF release you want
npm ci && npx vitest run && (cd desktop && npm run dev)
```

Conflicts are rare because Paperwing's code lives in its own folders. When they happen they're
usually in `vite.config.ts`, `package-lock.json` or repository files Paperwing replaced (README,
CONTRIBUTING, workflows, issue templates) — keep Paperwing's version of those.

Paperwing also removed BentoPDF's web-hosting files (Docker, nginx, Helm chart, Cloudflare and
Unraid configs, the air-gap bundle) and its documentation website. If upstream changed any of them,
the merge reports a modify/delete conflict; resolve it by keeping them deleted:

```bash
git status --short | grep '^DU' | cut -c4- | xargs git rm
```

After merging, look over a few tool pages in both themes: new upstream markup may need a small
addition to `src/reskin/reskin.css` or `apps.css`.
